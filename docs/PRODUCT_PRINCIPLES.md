# Product Principles

## One result, not many mechanisms

Users should understand workspaces, tasks, artifacts and memory. Profiles, provider routes, bundles, MCP servers and plugin package managers are implementation details.

## Durable work over chat theater

A task has a stable ID, plan, state, events, artifacts, proof and continuation path. Closing a browser must not redefine whether the work exists.

## Show evidence, not hidden reasoning

The product exposes actions, files, tests, decisions, approvals and verification evidence. It does not pretend that raw hidden chain-of-thought is a trustworthy product surface.

## Ask only when a human decision is valuable

Routine low-risk work proceeds. High-impact actions, unclear trade-offs and explicit approvals interrupt the user. Notifications are scarce by design.

## Memory must remain legible and correctable

The system proposes memories. The user approves, edits, rejects or deletes them. Current instructions and workspace evidence always outrank historical memory.

## Capabilities should disappear into the experience

Image understanding, model selection, subagents and verification should feel like normal product competence, not a configuration exercise.

## Safety is a continuous property

Security is not one modal before execution. It covers task intent, local posture, model-call policy, tool preflight, extension provenance and delivery evidence.

## Integrate, do not swallow

Excellent upstream projects should remain replaceable modules behind contracts. One does not duplicate their databases, rename their internals or trap them in a permanent source fork.
