# Security Model

## Trust assumptions

DeepSeek Harness One is a local single-user application in version 0.1. It assumes the operating-system account is trusted and defaults to loopback networking.

Do not bind it to `0.0.0.0` or a public interface without an authenticated reverse proxy, TLS, request limits and organization-specific authorization.

## Protected assets

- Workspace files.
- DSH credentials and profile configuration.
- Task prompts, outputs and event history.
- Approved memory.
- Artifacts generated by the agent.
- Extension installation authority.

## Implemented controls

### Network

- Default host: `127.0.0.1`.
- No permissive CORS headers.
- Content Security Policy on static assets.
- Server-Sent Events remain same-origin.

### Filesystem

- Static and artifact paths are resolved and containment-checked.
- Workspaces must already exist and are canonicalized with `realpath`.
- The demo workspace is isolated under One's data directory.

### Processes

- DSH is spawned using an argument array with `shell: false`.
- Workspace path becomes the child working directory only after registration.
- Cancellation sends a termination signal.
- Pause/resume use process signals only on supported POSIX systems.

### Persistence

- Event strings are secret-redacted before being appended.
- Memory refuses content when redaction indicates a likely credential.
- Atomic JSON writes use a temporary file and rename.

### Intent and approvals

High-impact signals such as destructive deletion, production changes, credential access, publication/deployment and financial actions place a task in `awaiting_approval` even when auto-run is enabled.

This intent classifier is a usability safety net, not a complete policy engine. Use OpenGuardrails and the official DSH approval pipeline for production enforcement.

### Extension lifecycle

- Registry entries are curated and include source, license and permission labels.
- Automatic installation is disabled by default.
- Guided integrations are never converted into arbitrary shell execution.

## Ecosystem Autopilot

The nightly ecosystem workflow treats all external repository metadata and README text as untrusted input. It does not clone, install, import or execute candidate code. Model-generated changes are limited to an allowlist of product paths and are rejected if they introduce protected-path edits, excessive scope, missing regression tests, credential-shaped material, new network or process capabilities, dynamic code execution, remote scripts, binary patches, symlinks or submodules.

The workflow can append at most one new optional integration registry entry and cannot rewrite existing entries. Product changes are prepared on an isolated branch, reviewed separately, validated on Node.js 22 and 24, and built as a Docker image before a pull request is eligible for merge. Missing model credentials degrade to discovery-only behavior.

## Local security scan

The built-in scan checks a bounded set of metadata:

- Non-loopback control-plane binding.
- Sensitive-looking files in DSH home and registered workspaces.
- Overly broad POSIX permission bits.
- Symbolic links and inaccessible scan locations.

It does not read or return secret values, execute plugin code or make remote connections. Use `dsh-security-audit` for a deeper DSH-specific report.

## Known limitations

- Version 0.1 has no multi-user authentication or RBAC.
- There is no deterministic full-content secret scanner.
- External workspace artifacts are listed but not served through One.
- Browser local storage and same-origin scripts remain part of the trusted UI boundary.
- A compromised DSH plugin runs with whatever authority its profile grants.

## Reporting

Do not open a public issue containing credentials, private prompts, workspace paths or exploit details. Follow the private reporting instructions in the root `SECURITY.md`.
